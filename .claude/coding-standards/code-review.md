# 代码审查规范

> Pull Request 审查必须遵循的规范。

## Pull Request 模板

**规则**: 每个 PR 必须使用标准模板。

```markdown
## 描述
简要描述此 PR 的目的和内容。

## 类型
- [ ] 新功能
- [ ] Bug 修复
- [ ] 重构
- [ ] 文档更新
- [ ] 性能优化

## 变更内容
- [ ] 变更点 1
- [ ] 变更点 2

## 测试
- [ ] 单元测试已添加/更新
- [ ] 集成测试已通过

## 检查清单
- [ ] 代码符合编码规范
- [ ] 代码已自审
- [ ] 注释清晰必要
- [ ] 文档已更新
- [ ] 无调试代码
- [ ] 无敏感信息

## 关联 Issue
Closes #123

## 截图/演示
（UI 变更提供截图）
```

---

## 审查检查清单

**功能性**:
- [ ] 代码实现了需求
- [ ] 边界情况已处理
- [ ] 错误处理完善
- [ ] 无明显 bug

**代码质量**:
- [ ] 命名清晰准确
- [ ] 逻辑简洁易懂
- [ ] 无重复代码
- [ ] 符合 SOLID 原则

**测试**:
- [ ] 测试覆盖充分（≥70%）
- [ ] 测试用例合理
- [ ] 测试可读性好

**性能**:
- [ ] 无明显性能问题
- [ ] 数据库查询优化
- [ ] 无内存泄漏

**安全性**:
- [ ] 无安全漏洞
- [ ] 输入已验证
- [ ] 敏感信息已保护

---

## 审查响应时间

| 优先级 | 响应时间 | 说明 |
|--------|---------|------|
| **紧急** | 2 小时 | 生产问题、阻塞发布 |
| **高** | 1 个工作日 | 重要功能、关键 bug |
| **中** | 2 个工作日 | 常规功能、优化 |
| **低** | 3 个工作日 | 重构、文档更新 |

---

## 审查反馈规范

**反馈类型**:

| 类型 | 说明 | 示例 |
|------|------|------|
| **必须修改** | 阻塞合并的问题 | 安全漏洞、严重 bug |
| **建议修改** | 最好修改但非阻塞 | 命名优化、代码简化 |
| **赞赏** | 值得学习的地方 | "这个实现很优雅" |
| **提问** | 需要澄清的地方 | "为什么选择这个方案?" |

**反馈语气**:

```
❌ 不好: "这代码写得什么垃圾"
✅ 好: "这段逻辑比较复杂，能否添加注释？"

❌ 不好: "重写"
✅ 好: "建议考虑使用工厂模式"
```

## PR 大小规范

| PR 大小 | 处理方式 | 建议 |
|---------|---------|------|
| **< 200 行** | 快速审查 | ✅ 理想 |
| **200-500 行** | 正常审查 | ✅ 可接受 |
| **500-1000 行** | 详细审查 | ⚠️ 考虑拆分 |
| **> 1000 行** | 拒绝审查 | ❌ 必须拆分 |

---

## 审查质量指标

| 指标 | 目标值 |
|------|--------|
| PR 平均大小 | < 400 行 |
| 审查响应时间 | < 24 小时 |
| PR 合并时间 | < 2 天 |
| 审查参与度 | 至少 1 人审查 |
| 代码覆盖率 | > 70%

---

## 审查流程

```
1. 提交 PR
   ↓
2. 自动检查（CI/CD）
   - 代码风格检查
   - 单元测试
   - 构建验证
   ↓
3. 代码审查
   - 至少 1 人审查通过
   - 所有审查意见已解决
   ↓
4. 合并
   - Squash merge 或 Rebase
   - 删除分支
```
